# docs-audit

检查项目文档与代码之间、文档彼此之间的漂移。优先沿用用户指定或当前任务已经明确的范围（某个子系统、某篇文档、某个目录）；范围确实不明时先问，不默认全仓扫描。

只要求检查时只读并报告；已有"检查并修复"授权时直接完成可证实的修正，不重复索要确认。设计取舍或业务行为变更另按用户授权处理。

## 0. 读项目约定

所有约定从当前仓库发现，不假定任何目录存在。在仓库根目录查看 `CLAUDE.md`、`AGENTS.md`、`README` 及它们指向的文档索引，弄清：项目有哪几类文档、各自的职责与写法规则、阅读路由指向哪里、是否自带文档检查脚本。项目规则与本技能冲突时以项目为准。

项目几乎没有文档时，只检查 `README`、`CLAUDE.md`、`AGENTS.md` 中的命令、路径和描述与代码是否一致。

## 检查项

1. **设计与代码**
   - 设计 / 架构文档里写的类型、接口、注册表、文件路径、状态与失败语义在代码中是否存在，有没有测试。
   - 搜不到的列出来，区分"新目标尚未实现"（应在状态里有差距记录）与"文档写错或过时"；不能搜不到就删掉目标，也不能凭文档宣称已实现。
   - 代码里新增的公共契约（新接口、新注册表、新数据格式）文档里有没有。
2. **状态与证据**
   - 标"已实现"的条目，引用的代码与测试是否还在，证据是否写明了实际跑过什么、在什么环境跑的。
   - 标"未实现 / 部分实现"的条目，代码里是否其实已经做了。
   - 历史结果不当作本轮复验；现有测试通过不证明新目标完成。
3. **职责与重复**
   - 规范里的规则如果在设计文档里已有等价契约，建议删掉或改成引用。
   - 同一契约在多处各写一份且措辞不同时，建议保留一处为权威，其余改为引用。
   - 规范引用的符号与路径是否真实存在。
4. **跨会话计划**
   - 每份进行中的计划：步骤是否已完成、结论是否已并入正文；可收尾的建议删除（确认归并完整后）。
   - 计划里的"下一步"与代码现状是否矛盾。
5. **入口与路由**
   - `CLAUDE.md`、`AGENTS.md`、文档索引里引用的目录、文件、章节和命令是否都存在；新增的源码目录有没有被路由覆盖。
6. **链接与历史**
   - 文档内相对链接与章节锚点是否有效。
   - 需要历史时用 `git log --all --full-history -- <path>` 和 `git show <commit>:<path>`，不恢复旧副本。

项目自带文档检查脚本时运行它；脚本结果只证明其检查范围，不代替语义审查。

## 报告格式

按检查项分组，每条一行：

```text
[类别] file:line — 文档目标与当前证据 — 问题及影响 — 建议改法或已做的修正
```

证据不足、无法判断的单列为"需确认"，写明缺什么证据。不把推测写成结论。

## 修改时

- 按条目小步修改，不整篇重写。保留类图、接口、字段、状态机、算法、正确性论证和测试点，只删纯历史与进度。
- 删除重复内容前，确认保留下来的那一处语义完整。
- 只做文档维护时不顺手改变业务行为。

最后报告实际检查的范围、做了的修正和剩余边界，不用审计结论代替实现证据。

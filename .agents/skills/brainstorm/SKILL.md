# brainstorm

在写代码前，把用户真正要的东西、范围边界、关键设计决策和验收标准问清楚，并落到项目文档里。本技能不是每个开发任务的前置流程。

默认只做查证、讨论与文档收敛，不改产品代码；用户已明确授权"讨论完直接实现"时沿用该授权，不重复要求"开始做"。

## 0. 读项目约定

所有约定从当前仓库发现，不假定任何目录存在。在仓库根目录查看 `CLAUDE.md`、`AGENTS.md`、`README` 及它们指向的文档索引，记下：

- 阅读路由与硬约束：分层、环境、禁止事项；
- 架构 / 设计文档、工程规范、实现状态、跨会话计划各放在哪，各自的写法规则；
- 没有对应约定的记为"无"。

项目规则与本技能冲突时以项目为准。

## 1. 先查证据

如果当前对话已有 `clarify` 需求单、`kickoff` 任务说明或其他已对齐的说明，以它为起点：已拍板的事不再问，只处理设计层面还没定的决策。

能从仓库回答的问题不问用户。按任务范围阅读：

1. 第 0 步找到的相关设计文档与规范；
2. 实现状态与已有的跨会话计划；
3. 相关代码、docstring、测试与资产；
4. 需要找回旧决定时，用相邻技能 `session-history`（检索到的技术判断只当线索）。

把发现分成：已确认的事实（附 `file:line`）、需要用户决定的意图与取舍、明显不在范围内的事。仓库只能说明现状和约束；用户想要的行为、范围边界和体验偏好，即使代码里已有类似模式，也要由用户决定。已有模式是选项和推荐依据，不是答案。

## 2. 一次处理一个决策点

问题按这个顺序推进，前四类没问清之前不急着让用户做选择：

| 类型 | 用途 | 例子 |
| --- | --- | --- |
| 现状 | 搞清实际发生了什么 | 现在是什么表现？给一个具体例子。 |
| 目标 | 找到真实目的，识别"描述的是方案而不是问题" | 做完之后什么会不同？不做会怎样？ |
| 对齐 | 复述理解，确认后再往下 | 我理解为 A，也可能是 B；A 会改 X，B 会改 Y。是哪个？ |
| 边界 | 拆开问题 | 哪些看起来相关但不要动？两者冲突时哪个优先？ |
| 选择 | 做决定 | 给出选项、推荐和取舍。 |

出现下面任一信号时，先问对齐问题，不按自己的理解往下走：

- 用户的词在代码或文档里另有含义；
- 用户描述的是方案而不是问题；
- 用户的例子和概括互相矛盾，或请求里两句话冲突；
- 目标和要求的改动对不上；
- 仓库里已经有用户要的东西（多半是理解错了）；
- 新意图可能推翻已有契约。

每个问题前写三行：发现了什么（`file:line` 或事实）、目前怎么理解、为什么这是现在最值得问的。选择题再加推荐与代价。推荐不是默认选项：不因为用户想尽快开工就替用户拍板。不问流程问题（要不要查、要不要继续）；查证直接做。

问答工具：Claude 用 `AskUserQuestion`；其他 agent 用当前模式提供的问答工具，异步提问时继续不依赖答案的查证；没有问答工具时在回复中提问，不假定另一工具存在。等待必要答案，不把沉默当作确认。

## 3. 收敛检查

结束讨论前逐条确认：

- 目标与用户价值写清楚了；
- 做什么、不做什么写清楚了；
- 验收标准是用户需求的可观察结果，不是自造的阈值、指标或测试数量（确实需要数字时问用户一次）；
- 用户需要决定的事都已拍板；
- 技术上的未知已查清，或明确延后并说明影响。

如果拍板的结果会推翻已有的决定（设计文档、规范或记忆里记过的），单独向用户确认，不把"同意你的推荐"当作同意推翻。

## 4. 写进文档

按第 0 步找到的项目约定回写，先检查已有条目，替换旧内容而不是追加副本：

- **设计决定**：写进项目的架构 / 设计文档，维护接口、数据流、状态与设计理由，写完整终态，不把实现进度写成架构。
- **新的工程规则**（代码推不出来的）：写进项目的规范文档，先找它替换的旧条目，不复制设计契约。
- **跨会话的大功能**：按项目约定保存目标与范围、已拍板决策、验收、剩余步骤；单会话能完成的改动不建计划。完成后把结论并入正文并删除计划。
- 目标与实现不一致时，按项目约定登记差距，不用一方直接覆盖另一方。

项目没有对应位置时，不自行建立文档体系：在回复里给出结论全文，并问用户要写到哪里。

最后给用户一份摘要：目标、范围内与范围外、验收、关键决策、风险或延后项、实际改了哪些文档。只授权讨论时到此结束，等用户明确说开始再实现；已授权继续实现时按已确认范围推进。不创建任务目录、JSONL 上下文或会话 journal。

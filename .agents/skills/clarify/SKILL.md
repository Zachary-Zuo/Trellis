# clarify

用户的原话往往是一句粗糙的意图：词不准、只说了方案没说问题、省掉了自己觉得显然的前提。用户也不知道 agent 缺哪些信息。这个技能的工作是把"用户脑子里的需求"和"agent 会实际做出来的东西"之间的差距找出来、摆到桌面上、逐个消掉。

对齐结束前不改产品代码，也不把猜测写入正式文档；查证（读代码、读文档、搜索）随时直接做，不问要不要查。用户已经明确的决定与授权不重新询问。

## 0. 读项目约定

所有约定从当前仓库发现，不假定任何目录存在。在仓库根目录查看 `CLAUDE.md`、`AGENTS.md`、`README` 及它们指向的文档索引，记下：阅读路由与硬约束；架构 / 设计文档、工程规范、实现状态、跨会话计划各放在哪（没有就记为"无"）。项目规则与本技能冲突时以项目为准。

## 1. 先查证，再复述

用户刚说完时不急着提问。按任务范围读相关的设计文档、规范、状态与计划、代码和测试。仓库能回答的事实不问用户；但用户想要的行为、范围和偏好必须由用户决定，已有实现只当推荐依据。

然后给出一份**理解草图**，让用户改草稿而不是从零描述。对粗糙的需求来说，挑错比口述容易得多：

```text
我听到的：<用一两句话复述用户想要的结果，用用户自己的词>
我理解要解决的问题：<问题本身；用户说的是方案时尤其要写>
准备采用的解读（逐条，可直接否决）：
  1. <解读> —— 依据：<file:line / 原话 / 标注为推测>
我原本会默默替你决定的事：
  - <agent 不问就会自己拍板的点>
仓库里已经定了、不用你管的：
  - <事实 + file:line>
```

"我原本会默默替你决定的事"是这个技能的核心：把 agent 的隐含假设显式化，用户才能看出缺口。写的时候问自己：如果现在直接开工，我会在哪些地方凭猜测选一个做法？

## 2. 找差距，只追问会改变结果的项

按下表逐项标"清楚 / 部分清楚 / 缺失"，只追问会改变做出来的东西或改变验收方式的项；不影响结果的按默认走，并在需求单里列出来。

| 维度 | 要弄清的 |
| --- | --- |
| 目标 | 做完之后什么会不同；不做会怎样；为什么是现在 |
| 现状 | 现在实际是什么表现；给一个具体例子 |
| 范围 | 做哪些；看起来相关但不碰哪些 |
| 术语 | 用户的词在代码和文档里是不是另有含义 |
| 约束 | 已有契约、已拍板决定、平台与验证边界 |
| 边界情况 | 失败、空、冲突、旧数据等情况怎么处理 |
| 交付面 | 代码、测试、文档各要不要动 |
| 验收 | 用户怎么判断"做对了"；可观察的结果，不自造阈值 |

出现下面任一信号时，先停下对齐，不按自己的理解往下走：

- 用户的词在仓库里另有含义；
- 用户描述的是方案而不是问题；
- 用户的例子和概括矛盾，或前后两句话冲突；
- 仓库里已经有用户要的东西（多半是理解错了）；
- 目标和要求的改动对不上，或有明显更简单的做法；
- 需求会推翻已有的设计、规范或决定。

要有立场：发现矛盾、更简单的方案、与已有决定的冲突时直接指出并说明理由，不顺着含糊表述往下写。推翻已有决定必须单独确认，"同意你的推荐"不算同意推翻；用户已明确要求的变更不再重复索要授权。

提问方式：

- 按"影响 × 不确定性"排序，最会改变结果的先问。
- 一轮把当前彼此独立的问题一起问；依赖别的答案的留到下一轮。每个问题带一行：发现了什么（`file:line` 或原话）、为什么问它。
- 问答工具：Claude 用 `AskUserQuestion`（推荐项放第一个并标"（推荐）"）；其他 agent 用当前模式提供的问答工具，遵守其题数与选项限制；没有问答工具时在回复里编号列出，用户可以按编号简短作答。
- 用户回答很短或含糊时，展开成具体解读让用户确认，不直接采纳。
- 用户说"你定""随便"时，给一个具体选择和理由，标"agent 默认，可调整"，继续往下。
- 每拿到一个答案就更新理解草图对应条目，不重复问已经定了的事。

不问流程问题（要不要继续查、要不要往下问）。剩下的未知都不会改变结果、用户说"够了"或希望立即执行时，停止提问；真正影响正确性且不能合理推定的未知明确列出，不把沉默当作答案。

## 3. 需求单

```text
目标：<解决什么问题；写问题本身，不只写方案>
范围：<做什么，以及哪些相关事项不在本次范围>
交付：<代码、文档、脚本或报告等形态，以及落在哪>
已拍板：<决定 + 理由或来源（用户原话、file:line）>
agent 默认：<可调整的选择 + 理由>
验收：<用户可观察的结果，以及如何验证>
约束与边界：<已有契约、环境、验证边界>
相关位置：<要读或要改的代码、文档与测试路径>
未决：<剩余未知及处理原则>
```

不自行发明指标、测试数量或额外功能。

## 4. 按用户意图交付

- **直接执行**：已授权执行且范围足够清楚时，按需求单推进，结束时逐条对照"验收"给出证据。新发现只在会改变结果且缺乏授权时提问，不自行扩展范围。
- **转 brainstorm**：需要定新的接口、数据格式或跨层契约，或要分多个会话做时推荐。读取相邻技能 `brainstorm`，以需求单为起点，已拍板的不再问。
- **生成 prompt**：用户要交给新会话时，输出自包含 prompt，结构为：一句话任务；背景（附 `file:line`）；目标 / 范围 / 不做；已和用户确认的决定（不要重新讨论）；agent 默认（可调整，改了要在汇报里说明）；验收；开工前先读的具体路径；约束；遇到需求单没覆盖的问题时哪些可自行决定、哪些必须停下问。只写结论和理由，不写讨论过程，不用"上面""之前"等指代，不把推测写成事实（没查证的标"未查证"）。写完按"一个从没参与讨论的 agent 拿到它会不会做错"读一遍，补上缺的前提。需求属于大功能时，在 prompt 里写明新会话先用 `brainstorm` 收敛设计。
- **只要需求单**：交付需求单后结束。

只有出口意图确实不明时才询问，不增加固定的"确认后才能继续"步骤。需要保存 prompt 时用用户指定位置；未指定时写到 agent 的临时目录（scratchpad）或项目已被 Git 忽略的目录，告知完整绝对路径，并在回复里给出全文。不引入会话 journal 或任务目录。

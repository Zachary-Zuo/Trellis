# Thinking Triggers

> 动手前对照本表：命中任何一条，就先停下来把对应的问题想清楚。
> 每条触发只给一句理由，具体判断留给当时读到的代码。

---

## 改任何值之前（先搜索）

```bash
grep -rn "value_to_change" .
```

理由：漏改一处是"忘了同步"类 bug 的主要来源，搜索比记忆便宜。

---

## Cross-layer

- [ ] 改动跨越 3 层以上（API、Service、Component、Database）——层边界是最容易出 bug 的地方。
- [ ] 同一份数据在层之间换了格式——每次转换都可能丢字段。
- [ ] 多个消费者需要同一份数据——各写各的解析迟早对不上。
- [ ] 不确定某段逻辑该放哪一层——放错层会让下一处改动重复一遍。
- [ ] 新增 event kind、JSONL 记录、RPC payload 或 config 字段——契约变了，只有读到它的代码知道。
- [ ] UI / 命令代码开始就地 cast 原始 payload 字段——同一个无类型字段被读到第 3 处之前，先建共享 decoder / type guard。
- [ ] 派生状态自己造游标——派生值必须指回源事件标识（`seq`、`id`、`version`）。

---

## Code reuse

- [ ] 正在写的代码和已有的很像——复制会让修 bug 只修一半。
- [ ] 同一个 pattern 已经出现 3 次以上——第 3 次是抽象的时机。
- [ ] 给多个地方加同一个字段——漏掉一处就是不一致。
- [ ] 修改任何常量或 config——常量必须有唯一来源。
- [ ] 新建 utility / helper 函数——先搜，可能已经存在。
- [ ] 基于 `kind` / `action` / `status` 的分支散落在多处 if/else——reducer 才是唯一的转移表；Python 的 if/elif 没有穷尽检查，新增 Literal 值会静默落到 `else`。

---

## 验证 AI cross-review 结论

- [ ] 说"用户输入可能恶意"——先看数据真实来源，内部 manifest 不是外部输入。
- [ ] 说"缺少校验"——数据来自可信内部源时不需要。
- [ ] 说"行为变了"——先读代码注释，可能是有意设计。
- [ ] 说"测试有 bug"——把被测功能删掉再跑，还过就是同义反复的测试。

理由：AI reviewer 有一定比例是误报，每条 CRITICAL / WARNING 都要对着代码确认过再处理。

---

## 写验收标准时

- [ ] 想写"覆盖率 ≥ X%"或"加 N 个测试"——这些指标证明不了需求被正确实现。
- [ ] 想写没人在意的数字阈值——需要数字时由用户给出。

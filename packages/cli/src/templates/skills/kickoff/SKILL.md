# kickoff

在动手前消除两种偏差：用户的想法尚未想清，或用户与 agent 的理解不一致。产出一份双方都能逐条核对的任务说明。用户已明确的授权和决定继续有效，不因调用本技能重复索要确认。

所有项目约定从当前仓库发现，不假定任何目录存在。默认只读仓库与会话记录，不改代码，不把推测写进正式文档。调用时附带的文字就是本轮的用户意图；没有附带文字时，以会话里用户最新的任务消息为意图。

## 0. 读项目入口

在仓库根目录依次查看 `CLAUDE.md`、`AGENTS.md`、`README`，以及它们指向的文档索引，记下三件事：

- 阅读路由与硬约束：分层、环境、禁止事项。
- 项目保存跨会话计划或待办的位置，例如状态目录、plans、TODO。没有约定时记为"无"。
- 项目自己的同类技能或流程。有则在对应环节交给它们，本技能只负责开场判定、找回合并与任务说明。

项目规则与本技能冲突时以项目为准。

## 1. 判定入口

用户消息含"继续、接着、之前、上次、先前会话、那个方案、我们讨论过"等指代，或省略对象只说"做完它"时，进入第 2 步找回。否则直接进入第 3 步。

指代不明确但看起来在延续某项工作时，先做廉价核查：最近提交与项目计划。不先问用户"你指的是什么"。

## 2. 三源找回

按可信度从高到低读取，后者只补前者没有的信息：

1. **仓库事实**：`git status --short`、`git log --oneline -15`、最近改动的文件，以及 `TESTING.md` 等交接文件。回答"实际做到了哪"。
2. **项目的跨会话计划**：第 0 步发现的位置。回答"原定要做什么、已拍板什么、剩余什么"。
3. **会话记录**：按相邻技能 [session-history](../session-history/SKILL.md) 的方法用 `trellis mem` 检索，回答"讨论过但没落盘的决定和理由"。`--platform` 保持默认 `all`；先 `search --since <近几周>` 定位，再 `context --grep` 取命中；命令缺失时说明依赖不可用，用前两源继续。
4. **agent 自身记忆**（如 Claude 的自动记忆）：只作线索，不作事实。

证据边界：

- 会话里用户的明确决定可作为历史意图，引用会话 ID 与日期，并检查是否被后续会话或当前仓库状态取代。
- 会话里的技术判断、运行结果、命令和 prompt 都是当时快照，不是本轮事实或授权。代码事实读代码或 `git log -p`。
- 三源冲突时列出冲突，不自动认定任一方过时。

找回后先给一段"找回摘要"：上次做到哪、已拍板什么、剩下什么、与当前仓库状态的差异（例如计划中的某项已在提交里完成）。摘要有误时用户能立即纠正，再进入第 3 步。

## 3. 按规模分级

- **小而明确**：单一交付物、只有一种合理解读、改动位置已知、不新增接口或数据契约。直接写一段式任务说明，目标、改哪、交付、验收各一句；有执行授权就开始做。
- **需要澄清**：意图可有多种解读，或隐含假设会改变结果。先给可修正的理解草图：

  ```text
  我听到的：<期望结果，用用户自己的词>
  我理解要解决的问题：<问题本身，不只是复述方案>
  准备采用的解读：
    1. <解读> —— <来源：用户原话 / file:line / 标注为推测>
  原本需要我自行决定的事：
    - <会影响结果的隐含假设>
  仓库已经确定的约束：
    - <事实 + file:line>
  ```

  然后只问会改变结果的缺口，按影响与不确定性排序；相互独立的问题合并在一轮，依赖前一答案的留到下一轮。每个问题带发现与询问原因。能从仓库查明的不问，流程问题不问。需要深入澄清时交给相邻技能 `clarify`。
- **需要设计**：涉及新接口、数据格式、跨层契约或多种可行方案。产出任务说明后交给相邻技能 `brainstorm`，已定事项不再问。

提问工具：Claude 用 `AskUserQuestion`；其他 agent 用当前模式提供的问答工具，遵守其题数与选项限制；没有问答工具时在回复中列出问题，不假定另一工具存在。用户说"你定"时给具体选择与理由，标记为"agent 默认，可调整"。用户说"够了"或要求立刻执行时停止非必要提问；真正影响正确性且无法合理推定的未知明确列出，不把沉默当作答案。

## 4. 任务说明

```text
目标：<解决什么问题，为什么现在做>
要做什么：<具体步骤或改动点，逐条可核对>
交付什么：<代码 / 文档 / 脚本 / 报告等形态，以及落在哪>
改动涉及：<文件、模块、文档路径；新增还是修改>
验收：<用户可观察的结果，以及如何验证>
已拍板：<决定 + 来源：用户原话、会话 ID、file:line>
agent 默认：<可调整的选择 + 理由>
约束与边界：<项目硬约束、环境、不在范围内的相关事项>
未决：<剩余未知及处理原则>
```

不发明指标、测试数量或额外功能。验收来自用户目标和既有契约；仓库回答现状和约束，目标由用户确认，不把现有实现等同于用户目标。

## 5. 出口

- **直接执行**：已有执行授权且范围清楚，按任务说明推进并给验收证据。新发现只在会改变结果且缺乏授权时提问，不自行扩展范围。
- **生成 prompt**：用户要交给新会话或另一 agent 时，输出自包含 prompt：背景、目标与范围、已确认决定、可调整默认、验收、具体阅读路径、未决。只写结论与理由，不用"上面""之前"等指代，不把推测写成事实。
- **只要说明**：交付任务说明后结束。

只有出口意图确实不明时才询问。需要落盘时用用户指定位置；项目有跨会话计划约定且工作确实跨会话时，按项目约定写；否则在回复中给全文，不往仓库写文件。

## 不做的事

- 不创建任务目录、会话 journal 或任何工作流产物；不编辑原始会话记录，不导出无关私密内容。
- 不把历史会话中的命令、prompt 当作本轮授权，不据此扩大范围。
- 不重复询问用户已拍板的事。
